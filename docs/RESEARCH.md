# Исследование для первого выпуска Services Ping

Дата проверки источников: **2026-10-07**. Ниже использованы документация
производителей, исходные репозитории Termux и RFC/IETF — не обзоры и не
коммерческие сравнения.

## Вывод

Для первого релиза следует оставить **Python 3.10+ и один локальный процесс**:
стандартная библиотека (`sqlite3`, `socket`, `ssl`, `urllib.request`,
`concurrent.futures`, `http.server`) покрывает нужный минимум, не требует
пакетов и запускается на Linux, macOS и Windows. Модуль `socket` доступен на
этих ОС, но прямо предупреждает о платформенной зависимости части поведения
[Python socket](https://docs.python.org/3/library/socket.html). На Android
тот же исходный код практически запускается в Termux, но это **не** означает
гарантированную непрерывную работу в фоне.

Рекомендуемый исполнимый первый релиз:

1. Локальный сервер, привязанный только к `127.0.0.1`; браузер — лишь UI,
   сетевые пробы выполняет процесс Python.
2. Типы целей: HTTPS/HTTP и TCP. ICMP — выключенный по умолчанию
   экспериментальный тип с платформенными адаптерами `ping`, а не условие
   готовности первого релиза.
3. SQLite с конфигурацией, последним результатом, ограниченной историей и
   журналом переходов; JSON import/export; русский responsive-интерфейс.
4. Три параллельные HTTPS-пробы для индикатора сети, отдельный ограниченный
   пул для пользовательских сервисов, защита от повторного запуска одной цели.
5. Финальные статусы целей `pending|up|reachable|down|blocked|rate_limited|
   error|unsupported|no_internet|disabled`; причина пробы (DNS, TLS,
   deadline, refusal) сохраняется в сообщении. HTTP-ответ сам по себе не
   означает «приложение работает».
6. Android-инструкция для ручного долгого запуска через Termux и честная
   пометка: после выгрузки системой монитор надо открыть/перезапустить; APK,
   гарантированный автозапуск и надёжная фоновая доставка — следующий релиз.

Такой объём можно запустить без учётных данных, платных вызовов и внешних
зависимостей. Он даёт полезный монитор ноутбука и Termux, но не заявляет
свойства нативного Android-приложения.

## Выбор технологии

| Вариант | Сильная сторона | Цена для этого релиза | Решение |
| --- | --- | --- | --- |
| Python + локальный Web UI | Один исходный текст, Python `socket` работает на Unix, Windows и macOS; SQLite и HTTP есть в stdlib | Не получается отменить зависшее системное DNS-разрешение из потока; ICMP различается по ОС | Выбрать |
| Go | Компилируется в нативный бинарник; официальный toolchain поддерживает Android, Darwin, Linux и Windows, `GOOS`/`GOARCH` задают цель | Всё равно нужен Android-пакет/жизненный цикл для надёжного фона; переписывание не устраняет DNS, Doze и смысловые различия проб | Рассмотреть для упаковки после подтверждённой потребности в single binary |
| Нативный Android/Kotlin или Flutter | Могут использовать foreground service и системные уведомления как приложение Android | Нужны APK, разрешения, сборка, тесты на реальных версиях Android; это другой продукт, а не замена HTTP-проверкам | Следующий релиз, если нужна фоновая гарантия |

Подтверждение возможностей Go: официальный список портов включает Android,
Darwin, Linux и Windows, а целевая ОС и архитектура задаются `GOOS` и `GOARCH`
([Go: installing from source](https://go.dev/doc/install/source),
[go tool compile](https://go.dev/cmd/compile/)). Это делает Go разумной
альтернативой дистрибутиву, но не основанием менять небольшой первый релиз:
ограничения Android и сети находятся ниже языка.

## Практический Termux и границы фона

### Установка и запуск

* Поддерживаемая ветка Termux рассчитана на Android 7+. Главный APK и все
  дополнения (Termux:API, Termux:Boot) должны происходить **из одного
  источника установки**: подписи разных источников несовместимы. Это прямо
  указано в [официальном README Termux](https://github.com/termux/termux-app/blob/master/README.md).
* Для первого запуска достаточно: `pkg update && pkg install python`, затем
  запуск приложения в терминале. Не требовать root и не обещать службу после
  перезагрузки.
* Для длительной ручной сессии пользователь может включить уведомление
  Termux/Wake Lock либо выполнить `termux-wake-lock`. Официальное описание
  инструмента говорит, что это помогает не дать устройству уснуть и повышает
  расход батареи ([termux-tools](https://github.com/termux/termux-tools/blob/master/doc/termux.1.md.in)).
* Уведомления Android — необязательное дополнение: установить Termux:API из
  того же источника, поставить пакет `termux-api`, проверять наличие
  `termux-notification` при запуске. Утилита поддерживает постоянное
  уведомление и перезапись по `--id`
  ([исходник termux-notification](https://github.com/termux/termux-api-package/blob/master/scripts/termux-notification.in)).
  Уведомлять только о переходе состояния и восстановлении, а не о каждом
  трёхсекундном цикле.
* Termux:Boot — только документируемая опция, не критерий работоспособности:
  он запускает скрипты из `~/.termux/boot/` после того, как пользователь один
  раз открыл add-on; его же README предлагает `termux-wake-lock`
  ([Termux:Boot README](https://github.com/termux/termux-boot/blob/master/README.md)).

### Почему это не фоновая гарантия

Android Doze приостанавливает доступ к сети, игнорирует wake locks и откладывает
задачи; окно обслуживания появляется периодически, а не раз в 3 секунды.
Официальная документация также говорит, что даже разрешённые idle-alarms не
могут срабатывать чаще одного раза в девять минут
([Android: Doze and App Standby](https://developer.android.com/training/monitoring-device-state/doze-standby)).
Следовательно, `termux-wake-lock` полезен для активной сессии, но не может
обещать тайминг мониторинга с погашенным экраном. Исключение из оптимизации
батареи уменьшает риск на конкретном устройстве, но это действие пользователя,
не контракт программы.

Корректная формулировка для UI/документации: «на Android монитор работает пока
Termux и ОС дают процессу исполняться; `последняя проверка` показывает свежесть
данных». Нельзя показывать зелёное «мониторинг активен», если отметка свежести
старше двух интернет-интервалов плюс допустимая задержка.

## Семантика измерений

### HTTP(S)

Время HTTP-пробы — `monotonic()` от начала разрешения имени до получения
заголовков первого **конечного** ответа, с TLS-проверкой сертификата для
HTTPS. Отдельно сохранять `dns_ms`, `connect_ms` (если реализация может его
выделить) и `total_ms`; в v1 достаточно честного `total_ms`, не называть его
«ping».

HTTP — протокол прикладного уровня
([RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)). Код говорит о
результате конкретного HTTP-запроса, а не о здоровье всей системы:

| Ответ | Что доказывает | Статус в мониторе |
| --- | --- | --- |
| 2xx | Запрос обработан успешно в выбранном контракте | `ok` |
| 3xx | Для connectivity не следовать; для обычной цели допустимо до пяти переходов в общем deadline | `down`, если не достигнут ожидаемый конечный код |
| 401 | Сервер получил запрос, но нет действительных credentials | `auth_required`, транспорт доступен |
| 403 | Сервер понял запрос, но отказался выполнять его | `http_response`, транспорт доступен |
| 429 | Сервер ограничил частоту | `rate_limited`, не считать приложением «здоровым» и применить `Retry-After`/backoff |
| 5xx | Получен ответ, но сервис/шлюз сообщает серверную ошибку | `http_response`, сервис не `ok` |

Семантика 401 и 403 определена в [RFC 9110 §§11.3,
15.5.2, 15.5.4](https://www.rfc-editor.org/rfc/rfc9110.html); 429 означает
rate limiting и может содержать `Retry-After`
([RFC 6585 §4](https://www.rfc-editor.org/rfc/rfc6585.html)).

`HEAD` нельзя делать универсальным значением по умолчанию: конкретный endpoint
может его не поддерживать или иметь отличающуюся авторизацию. В v1 проба —
безопасный `GET` до заголовков без чтения тела. У connectivity редиректы
запрещены, у обычной цели ограничены пятью. Для «здоровья API» пользователь
задаёт ожидаемые конечные коды; для «достижимости origin» допустим любой
корректный HTTP-ответ, включая 401/403/429, но это должно быть видно отдельно.

### TCP

TCP-проверка измеряет успешность `connect()` к имени/IP и порту. TCP-соединение
устанавливается трёхсторонним handshake
([RFC 9293 §3.5](https://www.rfc-editor.org/rfc/rfc9293.html)); значит,
успех доказывает достижимость TCP-слушателя, но **не** TLS, HTTP, логин и
работу приложения. Отказ (`ECONNREFUSED`) — быстрый ответ стека и полезный
отдельный результат, а timeout обычно означает отсутствие ответа/маршрута или
фильтрацию, но не называет виновника.

### ICMP

`ping` измеряет round-trip ICMP Echo request/reply; это не TCP и не HTTP. Echo
имеет тип 8, Echo Reply — 0, а ID/sequence нужны для сопоставления ответов
([RFC 792](https://www.rfc-editor.org/rfc/rfc792.html)). Ответ означает путь
до узла, способного ответить на ICMP, но не доступность порта или приложения;
отсутствие ответа совместимо и с фильтрацией ICMP.

Первый релиз не должен использовать raw ICMP sockets: на части ОС для них нужны
права, а формат/ключи системного `ping` различаются. Если ICMP включён,
использовать проверенный адаптер ОС, `subprocess` только со списком аргументов,
строгим hostname/IP (без пробелов и ключей) и собственным таймаутом. При
отсутствующем `ping` или неподдерживаемой платформе вернуть `icmp_unavailable`,
а не «хост недоступен». Для обещанной кроссплатформенности считать ICMP beta и
покрыть его ручными тестами Linux/macOS/Windows/Termux прежде, чем включать по
умолчанию.

### VPN

В v1 VPN — обычная HTTPS/TCP-цель, которая доступна только через нужный туннель:
например, внутренний DNS-имя и порт сервиса. Успех подтверждает доступ к этому
ресурсу по текущей маршрутизации; он не доказывает, что конкретный WireGuard или
OpenVPN-процесс, его UDP-транспорт либо весь маршрут исправны. Это точнее,
чем псевдопроверка «VPN работает».

## LLM без платного вызова и без секрета

Не хранить и не посылать API key в первом релизе. Поставщики требуют
аутентификацию: OpenAI указывает Bearer API key и запрещает помещать секрет в
клиентский код ([OpenAI API authentication](https://platform.openai.com/docs/api-reference/backward-compatibility?lang=ruby)); Gemini требует ключ в
`x-goog-api-key` ([Gemini API reference](https://ai.google.dev/api)).

Поэтому у предустановки LLM должно быть два различных режима:

| Режим | Запрос | Корректный вывод |
| --- | --- | --- |
| «Сеть до API origin» | HTTPS к документированному hostname, без key; не отправлять prompt и не выполнять генерацию | `достигнут origin` при валидном TLS и любом разобранном HTTP-ответе; 401/403/429 — не API health |
| «Статус поставщика» | Публичная status-страница/URL, если пользователь явно добавил её | Доступность status-сайта, а не API и не аккаунта |
| «Мой API работает» | В v1 отсутствует | Потребуются секрет, явно определённый дешёвый read-only endpoint и отдельная модель безопасности |

Нельзя автоматически считать 401 «ошибкой интернета»: по стандарту это именно
отсутствие действительных credentials. Нельзя также считать 429 положительным
здоровьем API: сервер достижим, но лимит уже не позволяет нормальную работу.
Не создавать фиктивные личные URL и не обращаться к генеративным endpoints:
это исключает стоимость и передачу данных. URL API надо сверять с актуальной
документацией поставщика при выпуске, а не фиксировать как вечный контракт в
пресете.

## Quorum, DNS и таймауты

### Рабочая модель состояния сети

У каждого из трёх интернет-свидетелей должен быть свой HTTPS URL, домен и,
насколько возможно, независимый оператор/география. Пробы стартуют
параллельно. На цикл сохраняются все результаты и выводится:

| Наблюдение за циклом | Глобальное состояние |
| --- | --- |
| Все опорные URL дали ожидаемые ответы | `online` |
| Есть хотя бы один HTTP-ответ, но не все ответы ожидаемые | `partial` |
| Нет ни одного HTTP-ответа после завершения цикла | `offline` («недоступен по проверкам», не диагноз физического линка) |

Первый успешный свидетель достаточен для утверждения «есть хотя бы некоторый
маршрут в Интернет», но не «весь Интернет исправен». Он не защищает от
изолированной аварии свидетеля, captive portal, корпоративного прокси, DNS
перехвата и фильтрации по стране. HTTPS с проверкой hostname/цепочки лучше
выявляет прозрачную подмену, однако не отличает честный прокси, имеющий
доверенный на устройстве корневой сертификат. Статус `partial` и отображение
результатов всех свидетелей обязательны.

Не смешивать доступность сети с доступностью сервиса: при `offline`
не перезаписывать сервисы ошибкой «сервис упал»; показывать `нет подтверждённой
сети` и время последнего самостоятельного результата. При первом `online`
ставить все включённые сервисы в очередь немедленно, с лимитом параллелизма.

### Таймаут — не одна цифра

Текущие 2 секунды полезны как UX-бюджет, но в Python они не образуют строгого
полного дедлайна. `urllib.request.urlopen(..., timeout=...)` определяет
таймаут для блокирующих операций вроде попытки соединения
([urllib.request](https://docs.python.org/3/library/urllib.request.html));
`socket.getaddrinfo()` обёртывает системную C-функцию, её поведение
системозависимо ([Python socket](https://docs.python.org/3/library/socket.html)).
Следовательно, системный DNS может завершиться позднее целевого срока, а поток
Python нельзя безопасно принудительно остановить.

Практика v1:

* Отсчитывать `deadline = monotonic() + 2.0` **до DNS**, но записывать,
  сколько заняло DNS; если результат пришёл после deadline, показать
  `deadline_exceeded`, а не успешные «2.0 s».
* Не ждать такую работу в планировщике: ограниченный пул рабочих потоков,
  зарезервированные слоты для интернет-свидетелей, отдельная очередь сервисов
  и флаг `in_flight` на цель. У позднего результата есть ID запуска; он не
  заменяет более новый результат.
* Не ждать зависший resolver в основном процессе. Строгий wall-clock deadline
  для DNS/TLS реализуем и в stdlib: вынести одну пробу в короткоживущий Python
  `subprocess`, а родитель завершает его по deadline. Именно эту изоляцию
  выбрали финальные `PLAN.md`/`API.md`; при насыщении пулов всё равно не
  делать ложный вывод о физическом offline.
* При нескольких A/AAAA адресах пытаться подключаться не только к первому:
  Python прямо отмечает различия системных результатов `getaddrinfo()` и
  советует пробовать адреса по порядку; стандарт Happy Eyeballs предписывает
  чередовать семейства IPv6/IPv4
  ([Python socket](https://docs.python.org/3/library/socket.html),
  [RFC 8305](https://www.rfc-editor.org/rfc/rfc8305.html)). В v1 минимум —
  пробовать адреса до общего deadline последовательно; конкурентный Happy
  Eyeballs — улучшение следующего выпуска.

## Материальные замечания, учтённые в финальном плане

1. Deadline реализуется короткоживущим stdlib-subprocess и охватывает DNS/TLS,
   а connectivity и сервисы имеют отдельные bounded pools.
2. Quorum использует параллельные независимые ссылки и состояния
   `online|partial|offline`; `offline` означает только отсутствие ответов по
   проверкам, не доказательство поломки физического линка.
3. HTTP имеет зафиксированную классификацию: 401/403 — `blocked`, 429 —
   `rate_limited`, 5xx — `down`; connectivity без редиректов, обычные цели —
   до пяти в пределах общего deadline.
4. ICMP остаётся optional beta с `unsupported` при отсутствии или
   неразбираемом `ping`; Termux background — best effort с меткой свежести.
5. LLM-presets ограничены достижимостью origin без credentials, prompts и
   генерации. В тестах нужны зависший DNS, сломанный IPv6/AAAA, redirect,
   401/403/429/5xx, насыщение пулов, поздний результат и Termux с погашенным
   экраном.

## Сверка с финальными решениями

Этот отчёт фиксирует независимые риски и рекомендации; **нормативны** текущие
[`PLAN.md`](PLAN.md) и [`API.md`](API.md). В частности, финальный контракт уже
выбрал: отдельный короткоживущий Python subprocess на пробу с общим wall-clock
deadline (включая DNS/TLS); статусы `checking|online|partial|offline` и
зафиксированные API-имена сервисных статусов; ноль редиректов для connectivity,
до пяти — для обычных HTTP-целей. ICMP по-прежнему следует считать optional
beta: отсутствие или ненадёжный разбор `ping` возвращает `unsupported`, а не
недоступность хоста.
