# Services Ping: план первого выпуска

## Требования

Локально проверять интернет и заданные пользователем сайты, VPS, VPN, BB и
LLM-провайдеров. Показывать задержки, доступность, историю и изменения состояния.
Быстро обнаруживать пропадание интернета и продолжать частые проверки до восстановления.
Настройки и история остаются на устройстве. Пользователь разрешил исследование,
чистые сабтреды, параллельную разработку, тесты, ревью, коммит и приватный GitHub.

## Предварительное решение (до независимой рецензии)

Python 3.10+ без обязательных сторонних зависимостей, локальный HTTP-сервер
на 127.0.0.1 и адаптивный русский интерфейс HTML/CSS/JS. Ноутбук: Linux/macOS/Windows.
Android: тот же процесс в Termux; отдельный APK — возможный следующий выпуск.
Браузер выполняет только запросы к локальному процессу; проверки сайтов выполняет Python.

HTTP(S), TCP и ICMP — разные виды проверки, задержка каждого подписана корректно.
HTTP 401/403/429 означает ответ сервера, но не успешную работу приложения/API.
ICMP может отсутствовать или блокироваться. VPN проверяется по заданному пользователем
доступному только через VPN адресу; это не доказательство работы UDP WireGuard/OpenVPN.
Никаких платных LLM-запросов, токенов доступа или выдуманных личных адресов.

## Состояния и расписание

Интернет проверяется отдельно от сервисов по нескольким независимым HTTPS-адресам,
включая российские и международные, по правилу «есть хотя бы один достоверный ответ».
Частичный доступ показывается отдельно; не объявлять отсутствие всего интернета по одному хосту.
Интервал проверки интернета 3 с, timeout 2 с; интервал сервисов 30 с по умолчанию.
Параллелизм ограничен. Нет перекрывающихся проверок одного сервиса.
При потере интернета сервисы получают состояние «нет интернета»/устаревшие данные;
при восстановлении проверяются сразу. Интернет проверяется независимо от медленных сервисов.
Стартовое состояние «проверяется»; потеря определяется за interval + ceil(reference_count/4)*timeout + overhead,
это конечная физическая граница требования «сразу».

## Настройки, хранение, интерфейс

Добавление/редактирование/удаление/отключение целей и групп, интервалы и timeout,
экспорт/импорт JSON. Предустановки Яндекс, Google, публичные LLM endpoints с явным
различием сетевой доступности и работоспособности API. Личные цели добавляются в UI.
SQLite: конфигурация, ограниченная история, журнал переходов. График задержек,
последняя проверка, причина ошибки, режим паузы и ручная проверка.
Заметное сообщение об offline и переходах; браузерные уведомления по кнопке,
опциональный Termux API notifier для Android; без спама на каждый цикл.

Локальный сервер проверяет Host и Origin, требует CSRF-token для изменения настроек,
ограничивает размер тела и статические пути, не выполняет команды из введённых строк.
ICMP через список аргументов subprocess, без shell. Настройки с секретами не включать в Git.

## Цикл разработки

1. Исследование с первичными источниками и сравнение вариантов.
2. Независимая рецензия этого плана в чистом BB-сабтреде; исправления до реализации.
3. Параллельные владельцы backend и frontend по согласованному API.
4. Unit/integration: классификация ошибок/HTTP-кодов, offline/recovery/partial,
   расписание, pause, CRUD/import/export, ограничения истории, защита localhost.
5. Браузерная smoke-проверка desktop/mobile и ручной локальный запуск.
6. Чистое независимое ревью кода; устранение существенных находок, повторные проверки.
7. Документация запуска на ноутбуке и Android, CI, коммит, приватный repo и push.

## Границы проверенного

Android background зависит от энергосбережения и ограничений ОС; документировать
wake-lock и Termux:API. APK и физический Android нельзя считать проверенными без сборки/устройства.
ICMP платформенные отличия и DNS deadline требуют отдельной проверки при рецензии.

## Уточнения архитектуры по предварительным замечаниям рецензии

- Каждый реальный probe запускается в отдельном короткоживущем Python subprocess
  с JSON по stdin и общим wall-clock deadline в родительском процессе. Это
  ограничивает DNS/TLS/редиректы, а не только socket.connect. Никакого shell.
- Отдельные ограниченные исполнители для connectivity и сервисов. Настройка
  concurrency относится к сервисам; connectivity имеет до 4 выделенных workers.
  Новые циклы connectivity не перекрываются со старым. Нет безграничной очереди.
- Отдельные поколения конфигурации и сетевого состояния: результаты удалённых/
  изменённых целей и проверки, завершившиеся после offline, не перезаписывают
  актуальное состояние. При смене состояния сети подменяется отображаемый статус,
  а последний реальный результат и время остаются в last_result; stale=true.
- checking при старте, online при успехе всех опорных проверок, partial при
  хотя бы одном успехе и хотя бы одном сбое, offline при отсутствии успехов.
  Connectivity использует HTTPS, без редиректов, с точными ожидаемыми кодами.
  offline означает отсутствие доступа к опорным адресам: UI прямо допускает
  проблемы DNS, фильтрацию и captive portal. Первое определение также даёт событие.
- На переходе offline одно событие интернета, без отдельных алертов для всех
  сервисов. Переходы реальных результатов сервисов записываются отдельно;
  уведомления отправляются только о смене статуса, с ограничением частоты.
- Ручная проверка в паузе выполняет один полный цикл и оставляет paused=true.
  Возобновление запускает немедленный цикл. Пауза не отменяет уже начатые probes.
- HTTP коды 401/403 всегда blocked, 429 всегда rate_limited, 5xx всегда down;
  остальные при непустом expected_statuses дают up только при совпадении.
  При пустом списке успешный HTTP ответ до 500 — reachable с healthy=null.
  TCP/ICMP дают up как успешный результат только своего типа проверки.
- SQLite хранит ограниченные samples на цель и не более 1000 событий; удаление
  цели очищает её историю. Изменение настроек транзакционное. Прокси из окружения
  отключены для воспроизводимости локального сетевого маршрута.
- Endpoint проверки не принимает команды/headers/секреты. HTTP URL без userinfo;
  localhost API проверяет Host/Origin, CSRF, размеры тела и пути. Ошибка браузерного
  соединения с локальным сервером отображается отдельно от offline интернета.

## Закрытие B1–B7 окончательной рецензии

- B1/B2: subprocess deadline, отдельные bounded pools, monotonic fixed-delay от
  завершения, coalescing одного ручного rerun. При >4 references циклы могут идти
  волнами; время обнаружения <= interval + ceil(reference_count/4)*timeout +
  небольшой overhead. Default 3 references даёт около 5 секунд.
- B3: корректировка агрегации — любой HTTP-ответ reference означает внешнюю
  связность. online — все ожидаемые ответы, partial — хотя бы один HTTP-ответ,
  но не все ожидаемые; offline — ни одного ответа. Неожиданный код/redirect
  отмечается как diagnostic partial. Намеренно без двухциклового hysteresis:
  пользователь просит быстрое обнаружение; вместо замедления честно показываем
  «недоступен по проверкам», причины, время и историю. Ограничение уведомлений
  сдерживает краткие колебания. Последнее измерение сохраняется отдельно.
- B4: GET до заголовков без чтения тела, обычные цели до 5 redirects в пределах
  общего deadline, проверка TLS обязательна; HTTP latency включает DNS/TCP/TLS
  до заголовков (без стоимости запуска helper), TCP включает DNS/connect,
  ICMP извлекает RTT из ping; unsupported если RTT не удалось надёжно извлечь.
  Неожиданный код при expected_statuses => down; сетевые/TLS/deadline ошибки =>
  down с reachable=false, healthy=false; отсутствующий ping => unsupported,
  healthy=null. TCP/ICMP up значит успех соответствующего сетевого теста.
- B5: точный Host с фактическим port, Origin absent допускается для CLI только
  с token, null/чужой Origin отклоняется. CSP self, frame-ancestors none,
  nosniff, UI textContent. Фиксированная map статических файлов. Body <=128 KiB,
  request line <=8 KiB, header total <=32 KiB, ограниченные request workers.
  Импорт на экране явно подтверждает применение полного списка адресов; проверки
  private/loopback разрешены (это обязательные пользовательские VPS/VPN/BB цели).
  Локальные процессы не входят в security boundary этого приложения.
- B6: data-dir задаётся --data-dir; default ~/.services-ping (Termux/Linux/macOS)
  или домашний каталог пользователя Windows. SQLite schema_version=1, writes
  сериализованы lock, config DB transaction перед сменой runtime revision.
  Retention per target, events max1000. При corrupt/locked DB ясная ошибка
  запуска/сохранения, без молчаливого reset. Экспорт только config version1.
  Ctrl-C прекращает scheduling и ограниченно дожидается probes перед close DB.
- B7: desktop первый подтверждаемый выпуск, Android best-effort Termux preview.
  Browser notifications — opt-in на странице, выбор хранится только в браузере;
  config.settings.notifications — отдельно опциональный Termux notifier.
  Уведомления global offline/recovery, без каскада сервисов; initial offline
  видно баннером, notification возможна при активированном backend notifier.
  Cooldown минимум10 с, ошибки отправки не блокируют scheduler. На телефоне
  проверка установки/screen-off/reboot остаётся явно непроверенной.

Snapshot включает config_revision и target.in_flight; данные под общей блокировкой.
History v1 только для service targets; интернет получает журнал событий и текущее
состояние references. Desktop tray/autostart и нативный APK за пределами выпуска.
