# Независимая рецензия `docs/PLAN.md`

Дата рецензии: 2026-10-07. Учтён также контракт `docs/API.md`.

## Вердикт

Направление первого выпуска разумное: локальный процесс, UI на loopback, разделение
проверки интернета и целей, SQLite и честная оговорка про Termux лучше, чем попытка
сразу обещать APK. Однако план **пока не готов к реализации**. В нём не определены
несколько свойств, от которых напрямую зависят сроки обнаружения, ложные offline,
безопасность локального API и совместимость backend/frontend. Если начать параллельную
разработку сейчас, эти решения почти наверняка будут приняты независимо и окажутся
несовместимыми.

Ниже «блокер» означает, что до начала реализации нужно исправить план и, где указано,
`docs/API.md`. Это рецензия архитектуры, не требование реализовать все возможные функции.

## Блокеры

### B1. `timeout_s` не является сквозным deadline, особенно для DNS

`socket`/`urllib` timeout не гарантирует ограничение времени системного
`getaddrinfo()`. Зависший resolver может пережить 2 секунды, занять worker и при
повторении исчерпать весь пул. Тогда обещанная граница «интервал плюс timeout» неверна.
Кроме того, у HTTP есть несколько фаз: DNS, connect, TLS, запись запроса, заголовки и
redirect. Timeout каждой фазы по 2 секунды также не даёт общего лимита 2 секунды.

**Исправление:**

- определить `timeout_s` как один monotonic deadline на всю попытку, а не timeout
  каждой операции;
- отдельно описать механизм ограничения DNS. Если остаётся только stdlib, честно
  выбрать одно из двух: изолируемая и принудительно завершаемая helper-проверка либо
  bounded DNS executor с жёстким пределом зависших работ и явной оговоркой, что
  системный вызов отменить нельзя;
- не создавать новый поток на каждый просроченный DNS; установить верхнюю границу
  незавершённых DNS-задач и состояние диагностической перегрузки;
- запускать независимые connectivity references параллельно под общим deadline,
  иначе три адреса с timeout 2 с дадут до 6 секунд только на один цикл;
- добавить тест с намеренно зависающим resolver и проверить, что scheduler, API и
  следующие connectivity-циклы остаются отзывчивыми;
- переписать обещание времени обнаружения: указать формулу с числом подтверждающих
  циклов и отдельно отметить пределы системного DNS, если он технически не прерывается.

### B2. Независимое расписание заявлено, но архитектурно не обеспечено

Один общий `concurrency=4` не гарантирует независимость: четыре медленные цели могут
занять все worker slots, а проверка интернета будет ждать. Не описаны очередь,
приоритеты, поведение при пропущенных тиках, перезапуск конфигурации и защита от
перекрытия manual/scheduled check.

**Исправление:**

- зафиксировать отдельный scheduler connectivity и зарезервированную для него
  ёмкость, не используемую сервисами; HTTP-сервер также не должен выполняться в этом
  пуле;
- рассчитывать расписание по monotonic clock; wall clock использовать только для
  сохраняемых timestamp;
- выбрать политику `fixed delay` или `fixed rate`. Рекомендуется fixed delay после
  завершения попытки с coalescing: накопившиеся тики не образуют очередь;
- гарантировать максимум одну активную попытку на reference/target; ручная проверка
  присоединяется к активной либо ставит один coalesced rerun, но не создаёт дубль;
- применять результат только к той ревизии конфигурации, на которой он был запущен,
  чтобы удалённая или изменённая цель не появилась снова из позднего callback;
- определить, что делает `POST /api/check` во время pause. Рекомендуется вернуть
  явную ошибку (например, 409) либо документировать один отложенный запуск; текущее
  `{"ok":true}` противоречит «pause stops new checks»;
- добавить тест насыщения service-пула и доказать верхнюю границу запуска
  connectivity check.

### B3. Нет полной машины состояний интернета и защиты от ложного offline

Фраза «есть хотя бы один достоверный ответ» недостаточна. Не определено, когда
получаются `online`, `partial`, `offline`, сколько неуспешных циклов подтверждают
offline, и считается ли неожиданный HTTP-код доказательством интернет-связности.
Три HTTPS URL независимы по владельцам, но разделяют локальный DNS, CA store, firewall
и часть маршрута. Поэтому одновременный провал не доказывает потерю физического линка.

**Исправление:**

- формально описать агрегацию одного цикла. Рекомендуемый минимум: любой завершённый
  HTTP-ответ доказывает внешнюю связность; все ожидаемые ответы — `online`; смесь
  успешных и неуспешных references — `partial`; отсутствие любого HTTP-ответа после
  завершения всех references — кандидат в `offline`;
- добавить hysteresis: первый полностью неуспешный цикл даёт переходное состояние
  «подтверждаем недоступность» (можно использовать `checking`, но это надо отразить в
  API/UI), `offline` — после заданного числа последовательных полных провалов.
  Восстановление допустимо подтверждать одним достоверным ответом;
- явно вывести фактическую верхнюю границу обнаружения при выбранном hysteresis.
  Нельзя одновременно обещать подтверждение двумя циклами и прежние 5 секунд при
  интервале 3 с и deadline 2 с без отдельного немедленного confirmation probe;
- хранить и показывать причины по каждому reference: DNS, connect, TLS, timeout,
  неожиданный HTTP. Текст `offline` должен оставаться тем, что уже требует API:
  «Интернет недоступен по проверкам», а не «физическое соединение отсутствует»;
- при глобальном offline не записывать фиктивные latency/history samples для каждой
  цели и не рассылать до 100 уведомлений `up -> no_internet`. Нужен один глобальный
  переход, а последнее реальное измерение цели остаётся доступным как stale;
- расширить snapshot явными `stale`/`last_measured_status` (или эквивалентом).
  Одного старого `checked_at` недостаточно: frontend иначе вынужден угадывать;
- определить поведение уже запущенных service checks при переходе в offline и порядок
  применения их результатов.

### B4. HTTP-семантика определена лишь частично

`docs/API.md` правильно выделяет 401/403 и 429, но не задаёт полную таблицу. Неясны
redirect, 1xx, 204/3xx/4xx вне `expected_statuses`, TLS/DNS/connect errors, чтение тела
и отличие `down` от `error`. Без этого backend и UI будут по-разному понимать
`reachable`, `healthy` и `status`.

**Исправление:** добавить в контракт нормативную таблицу для всех исходов:

| Исход HTTP-проверки | `reachable` | `healthy` | `status` |
|---|---:|---:|---|
| Код входит в непустой `expected_statuses` | true | true | `up` |
| Любой обычный HTTP-ответ при пустом списке, кроме специальных кодов ниже | true | null | `reachable` |
| 401 или 403 | true | false | `blocked` |
| 429 | true | false | `rate_limited` |
| 5xx | true | false | `down` |
| Иной код вне непустого ожидаемого списка | true | false | заранее выбранное одно состояние |
| DNS/connect/TLS/общий deadline | false | false или null по формальному правилу | заранее выбранное `down` либо `error` |
| Неподдерживаемый kind/нет `ping` | false | null | `unsupported` |

Специальные 401/403/429 должны иметь приоритет над пользовательским
`expected_statuses`, как уже сказано в API. Это сознательно означает: endpoint
доступен, но работоспособность приложения не подтверждена. Для 5xx тоже нельзя
терять `reachable=true`.

Также нужно определить:

- выполняется GET, HEAD или настраиваемый метод; для v1 лучше один GET;
- redirect policy и максимальное число переходов; итоговый URL и причина должны быть
  диагностируемы, общий deadline не перезапускается;
- тело ответа либо не читается, либо читается до малого фиксированного лимита; нельзя
  скачивать бесконечный ответ или распаковывать неограниченный gzip ради ping;
- проверяется TLS по системному trust store, а отключение проверки сертификата не
  поддерживается;
- точная семантика TCP и ICMP для тех же трёх полей. Парсинг текста `ping` не должен
  считаться переносимым без таблицы Linux/macOS/Windows/Termux; отсутствие бинарника
  — `unsupported`, а не падение всего monitor.

### B5. Защита локального сервера пока декларативна

Bind на `127.0.0.1` снижает поверхность атаки, но browser-based DNS rebinding, CSRF,
XSS из имён целей и злоупотребление импортом устраняются только точными правилами.
CSRF token не является защитой от другого локального процесса; это ограничение нужно
сказать прямо.

**Исправление:**

- сервер слушает только IPv4 `127.0.0.1`; UI открывается по напечатанному сервером
  точному URL. Если нужен IPv6 `::1`, это отдельный listener и отдельная проверка;
- разобрать `Host` строгим parser'ом и принимать только точные `127.0.0.1:PORT` и
  `localhost:PORT` с фактическим портом, без suffix, userinfo, неоднозначных IPv4 и
  нескольких значений;
- для mutation требовать одновременно непредсказуемый token текущего процесса и,
  если запрос браузерный, точный разрешённый `Origin`; чужой/`null` Origin отклонять.
  Уточнить поведение отсутствующего Origin для CLI-клиента;
- не включать CORS, JSONP и mutation через GET; добавить CSP (`default-src 'self'`),
  запрет framing и MIME sniffing;
- все пользовательские строки в UI вставлять через `textContent`, не `innerHTML`;
- установить числовые лимиты request line, заголовков и body; JSON должен отвергать
  лишние/неверные типы, дубли IDs и неизвестную версию до записи;
- статические файлы отдавать только из фиксированной map/корня после нормализации;
  проверить traversal как в URL, так и после percent-decoding;
- задокументировать redirect к private/loopback адресам. Поскольку пользователь сам
  задаёт цели, это не классическая удалённая SSRF, но импорт конфигурации не должен
  молча превращаться в привилегированный сканер без явного подтверждения;
- добавить negative integration tests: DNS-rebinding-style Host, foreign/null Origin,
  token mismatch, oversized body, traversal, stored XSS и malformed import.

### B6. Persistence не имеет достаточного контракта

«SQLite: конфигурация, ограниченная история, журнал переходов» не определяет атомарность
между runtime и БД, миграции, retention и восстановление после сбоя. В API неясно,
`history_limit` действует на каждую цель, на все цели вместе или на один запрос;
retention events вообще не ограничен.

**Исправление:**

- выбрать и документировать каталог данных отдельно от исходников для Linux, macOS,
  Windows и Termux, права файла и способ переопределения пути;
- ввести `schema_version`, последовательные миграции и транзакцию для полного
  `PUT /api/config`: сначала validate, затем одна DB transaction, затем атомарная смена
  runtime revision; при ошибке старая конфигурация продолжает работать;
- сериализовать записи одним DB owner/queue либо формально описать threading model;
- определить retention отдельно: например, последние `history_limit` реальных samples
  **на цель** и отдельный конечный `events_limit`; pruning выполняется транзакционно;
- не сохранять `no_internet` как измерение latency и не менять `checked_at`, если
  проверка не запускалась. Если такие переходы нужны в events, хранить их только там;
- определить, создаёт ли изменение текста ошибки event. Рекомендуется event только
  при смене нормализованного состояния, иначе журнал и уведомления будут шумными;
- экспорт v1 должен явно включать только конфигурацию, не историю, CSRF token и
  runtime state. Импорт неизвестной версии отклоняется без частичного применения;
- описать поведение при locked/corrupt DB и понятную пользователю ошибку. Для v1
  достаточно документированного backup/export пути; обещать автоматическое
  восстановление без дизайна нельзя;
- уточнить, что «остаётся на устройстве» не означает сохранность после удаления
  Termux/очистки его данных; пользователю нужен экспорт во внешнее хранилище.

### B7. Уведомления и Android обещаны шире, чем позволяет выбранная платформа

Browser Notification без service worker и живой страницы не является фоновым
уведомлением. Termux-процесс может быть остановлен Android; wake-lock уменьшает риск,
но не гарантирует непрерывность при Doze, force-stop, очистке процесса или reboot.
`settings.notifications` сейчас одновременно выглядит как общая настройка и как
переключатель backend Termux notifier, тогда как browser permission хранится и
контролируется браузером.

**Исправление:**

- сузить Android v1 до «интерактивный/foreground best-effort монитор в Termux»;
  не заявлять надёжный background monitoring, автозапуск или работу после reboot;
- в документации дать проверяемую матрицу: установленный Python, запуск сервера,
  доступ браузера к `127.0.0.1`, screen-off, battery optimization, wake-lock,
  наличие команды Termux:API и разрешение уведомлений. Непроверенные пункты пометить
  как ограничения, а не возможности;
- отсутствие Termux:API или разрешения — диагностируемое `unsupported/disabled`, а не
  ошибка основного цикла. Вызов notifier только argv без shell и с deadline;
- развести browser opt-in и backend notifier. Browser permission нельзя получить
  автоматически: только user gesture, обработка `default/denied/granted`; backend
  настройка должна иметь отдельное имя;
- определить уведомляемые переходы. Рекомендуемый v1: подтверждённый global offline,
  recovery и выбранные пользователем цели; без initial/pending/no_internet cascade;
- дедупликация по transition, cooldown и coalescing обязательны. Ошибка отправки
  уведомления не меняет статус сети;
- явно написать: браузерные уведомления работают только пока UI открыт и выполняет
  polling; backend Termux notification — только пока жив monitor process;
- APK, Android service, WorkManager, foreground-service notification и boot receiver
  исключить из v1. Их нельзя считать естественным продолжением того же Python-процесса
  без отдельной архитектуры и теста на физическом устройстве.

## Важные уточнения до заморозки API

1. Добавить `config_revision` и/или generation к snapshot, чтобы UI и scheduler могли
   отличить поздние результаты старой конфигурации.
2. Описать snapshot во время активной проверки. Фраза «показывает remaining in-flight
   results as such» не поддержана полями API: нужны `checking`/`in_flight` и сохранённое
   последнее измерение, а не уничтожение предыдущего статуса.
3. Определить консистентный снимок `/api/state`: одна блокировка/immutable snapshot,
   чтобы список целей, settings и результаты относились к одной ревизии.
4. Зафиксировать значения `latency_ms`: для HTTP это время до заголовков или до первого
   байта, для TCP — connect latency, для ICMP — RTT. Не сравнивать их как одну метрику.
5. Уточнить формат timestamp (UTC Unix seconds, допустима ли дробная часть) и источник
   времени. Расписание никогда не должно зависеть от перевода системных часов.
6. Ограничить частоту polling и mutation не только в UI: локальный клиент может создать
   нагрузку. Достаточны bounded request handling и coalescing manual check.
7. `GET /api/history?target_id=...` должен уметь адресовать интернет/references либо
   контракт должен прямо сказать, что история доступна только для service targets.
8. Конфигурация требует как минимум два connectivity URL, но нужно определить поведение
   при отключении/удалении, невозможной комбинации bounds и старой импортируемой версии.
9. Public presets, особенно LLM endpoints, должны быть только reachability presets.
   Нельзя интерпретировать 401/403 как исправность API, делать платный запрос или
   хранить token. Это уже верно по смыслу плана, но должно быть закреплено тестом.
10. Нужен graceful shutdown: перестать принимать mutation, остановить новые проверки,
    ограниченно дождаться активных, завершить DB writer. Иначе «данные остаются на
    устройстве» не проверяемо при обычном Ctrl-C.

## Минимальный набор приёмочных сценариев для пересмотренного плана

- Все service workers заняты, но connectivity cycle стартует в установленный срок.
- Resolver завис; UI/API отвечают, число фоновых задач ограничено, следующий цикл не
  вызывает неограниченный рост потоков.
- Один reference успешен, два неуспешны; все неуспешны один цикл; подтверждённый
  offline; восстановление одним ответом. Для каждого случая заранее известны state,
  event и notification.
- Цель была `up`, интернет стал offline: старое измерение осталось с исходным
  `checked_at`, цель помечена stale/no_internet, нет фиктивной latency и notification
  storm.
- 200 expected, 204 unexpected, 302, 401, 403, 404, 429, 500, DNS failure, TLS failure
  и deadline дают точно оговорённые `status/reachable/healthy`.
- Pause во время активных работ, manual check во время pause, resume и изменение/
  удаление цели при позднем результате имеют детерминированный исход.
- Некорректный import, сбой записи и старая schema не меняют рабочую конфигурацию
  частично.
- Чужой Host/Origin, неверный token, oversized body, traversal и HTML в имени цели
  безопасно отклоняются или отображаются как текст.
- Browser notification denied и отсутствующий Termux notifier не нарушают monitoring;
  один переход не создаёт повторных уведомлений на каждом poll.
- Ручной запуск проверен хотя бы на одной desktop ОС. Android/Termux помечается
  проверенным только после теста на физическом устройстве; до этого это поддерживаемый
  сценарий установки с перечисленными ограничениями, а не подтверждённая платформа.

## Рекомендация

**Не начинать параллельную реализацию backend/frontend до второй версии плана и API.**
Сначала закрыть B1–B7, прежде всего: сквозной deadline/DNS, резервирование scheduler,
формальную state machine с hysteresis, полную HTTP-матрицу и stale-модель. После этого
заморозить `docs/API.md`, выписать перечисленные приёмочные сценарии и только затем
делить владельцев backend/frontend.

Для первого выпуска рекомендую сохранить desktop как подтверждаемую основную платформу,
а Android сформулировать как best-effort Termux preview. Повышать Android до заявленной
поддержки следует после проверки установки, screen-off, уведомлений и восстановления
на физическом устройстве. При таком сужении scope архитектура остаётся реалистичной и
не требует преждевременно обещать APK или надёжный Android background service.

## Повторная рецензия после исправлений

Повторно проверены актуальные `docs/PLAN.md` и `docs/API.md`. Архитектурные B1–B7
содержательно закрыты. Решение не вводить hysteresis допустимо для v1: `offline`
теперь честно означает отсутствие HTTP-ответа от всех опорных адресов, а не доказанную
потерю физического линка; быстрый переход, диагностический текст, история и cooldown
уведомлений образуют согласованный компромисс.

Перед реализацией остаются только следующие существенные противоречия текста:

1. Пример snapshot в `API.md` всё ещё не содержит нормативно добавленные
   `config_revision`, `target.in_flight`, `target.stale` и `target.last_result`.
   Нужно обновить JSON-пример и точную форму `last_result`, иначе frontend может
   правомерно реализовать старую схему.
2. Раннее утверждение API «пустой `expected_statuses`: любой HTTP-ответ, health
   unknown» противоречит позднему приоритету 401/403/429/5xx. Нужно заменить его на
   точное правило: специальные коды всегда сохраняют `blocked`/`rate_limited`/`down`,
   а `reachable, healthy=null` применяется только к остальным HTTP-ответам.
3. Раннее обещание плана «потеря определяется в пределах interval + timeout» неверно
   при 5–10 references и пуле из четырёх workers. Единственной нормативной формулой
   должна остаться поздняя `interval + ceil(reference_count/4) * timeout + overhead`.
4. План требует ясной ошибки при locked/corrupt DB во время сохранения, но список
   ошибок API допускает только 400/403/413/404/405. Следует добавить JSON-ошибку 500
   (либо выбранный 503) для сбоя persistence; молчаливое сохранение только в runtime
   недопустимо.

**Итог: условный GO.** После этих четырёх редакционных исправлений план и API готовы
к реализации; нового архитектурного цикла рецензии не требуется. Android остаётся
best-effort Termux preview, как теперь явно зафиксировано.
